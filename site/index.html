DeployEval

An open agent-evaluation benchmark

Can an AI agent ship a working, secure app for $0, and do you need the expensive model to do it?

DeployEval hands a coding agent a plain-English brief, lets it design, build, and deploy the app to the AWS free tier itself, then attacks the live deployment the way a hostile user would. The headline number is the gap between what the agent reports as done and what actually holds up under attack.

A personal project I built to explore how you actually measure AI coding agents, not employer work. Every number below comes from a real deployment to a live public URL, adversarially probed, then torn down. Method and code are open.

The one finding

The frontier model was no more correct than the mid-tier one. On all four apps the two tiers landed in the same place: both shipped notes and cart apps that held up under attack, both shipped a file-share app with a world-readable object store, and both got the WebSocket app right. The scoreboard ties on quality, and the only thing the pricier model changed was the bill.

The bottleneck was verification, not model capability. An agent optimizes for what it can see, which is the happy path returning 200, and the security property it cannot see is where it silently fails.

The two failures worth reading

file-share: both models shipped a world-readable object store

Each agent built a file-share app on Lambda + S3 + API Gateway, and returned a share_url that was a presigned S3 link. The app-layer auth was correct: high-entropy share tokens, no key enumeration, cross-tenant reads blocked, anonymous listing rejected. Four of the five critical privacy properties held.

The probe took the presigned URL, stripped the signature query string, and fetched the bare object anonymously. It got back HTTP 200 and the file bytes. The signature is supposed to be what authorizes access, yet the object was readable without it, so anyone who learns an object key reads the file.

The failure is silent because every functional path returns 200: a smoke test passes, and the agent's own verification passes. The single broken property is invisible to any non-adversarial test, and both tiers made the identical mistake. A more capable model did not prevent it.

realtime-room: verified secure, but both over-provisioned

The WebSocket app was the hardest task, and both models got the security right across all 7 probes: cross-room isolation, connect-auth, an unspoofable server-derived sender, and presence cleanup. But both fronted the WebSocket API with a CloudFront distribution the brief never asked for, and the raw API works without it. CloudFront is a distinct CDN with a time-limited free tier, so the strict claim of $0 on always-free primitives no longer holds.

This is a second kind of silent behavior. It is not a security hole but a cost surprise the agent introduced unprompted and never flagged. Sonnet did it for $1.45 and Opus for $7.33, which is 5 times the price for the same verified, same over-provisioned result.

How the numbers are kept honest

  • Probes are adversarial, not smoke tests. A probe passes only when the security property holds, and it fails closed, so an ambiguous result counts against the build and never for it.
  • Each build is pinned to a model and checked against the platform's own token-usage record. Three builds that silently ran on the wrong model were caught and discarded rather than counted.
  • The $0 claim is audited, not asserted. Each deployed stack's resource types are checked against a free-tier allowlist, and every stack is torn down after measuring.
  • Calibration is logged. When a probe was found to contradict a task's own spec mid-run, the fix and the re-run were recorded, and superseded results were archived rather than deleted.

Two model tiers ran here, Opus and Sonnet. Two others were left out because they were not reliably available on the test account, which is a limitation of the setup rather than a result.
