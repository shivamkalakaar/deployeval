DeployEval

An open agent-evaluation benchmark

Can an AI agent ship a working, secure app for $0, and do you need the expensive model to do it?

DeployEval hands a coding agent a plain-English brief, lets it design, build, and deploy the app to the AWS free tier itself, then attacks the live deployment the way a hostile user would. The headline number is the gap between what the agent reports as done and what survives the attack.

A personal project I built to explore how you measure AI coding agents, not employer work. Every number below comes from a live public URL, adversarially probed, then torn down. Method and code are open.

What the results show

All four tiers scored the same: three of four apps verified, one silent failure each. The newest frontier model (Opus 5) matched a prior-generation mid-tier one (Sonnet 4-6) on correctness. Every model shipped working notes, cart, and WebSocket apps that survived attack, and every model shipped a file-share app with a world-readable object store. The four models tied on quality and differed only in cost.

Verification was the limiting factor here more than model capability. An agent optimizes for what it can see, the happy path returning 200, and the security property it cannot see is where it silently fails.

The file-share failure, in detail

file-share: every model shipped a world-readable object store

Each agent built a file-share app on Lambda + S3 + API Gateway and returned a share_url that was a presigned S3 link. The app-layer auth was correct: high-entropy share tokens, no key enumeration, cross-tenant reads blocked, anonymous listing rejected. Four of the five critical privacy properties held.

The probe took the presigned URL, stripped the signature query string, and fetched the bare object anonymously. It got back HTTP 200 and the file bytes. The signature is supposed to be what authorizes access, yet the object was readable without it, so anyone who learns an object key reads the file.

The failure is silent because every functional path returns 200: a smoke test passes, and the agent's own verification passes. The single broken property is invisible to any non-adversarial test. All four models made the identical mistake, across two generations and both the frontier and mid tiers. A newer or larger model did not prevent it.

How the numbers are checked

  • Probes attack the running app rather than checking that it returns 200. A probe passes only when the security property holds, and it fails closed, so an ambiguous result counts against the build.
  • Each build is pinned to a model and checked against the platform's own token-usage record. Builds that silently ran on a fallback model were caught and discarded rather than counted.
  • The $0 claim is audited: each deployed stack's resource types are checked against a free-tier allowlist, and every stack is torn down after measuring.
  • Calibration is logged. When a probe was found to contradict a task's own spec or misread a valid response shape, the fix and the re-run were recorded, and superseded results were archived rather than dropped.

Four Claude tiers ran here (Opus 5, Opus 4.8, Sonnet 5, Sonnet 4-6). Two smaller Claude tiers were left out because they were not reliably available on the test account, and an open-weight model (Qwen3-Coder) was piloted through a separate agent harness but set aside as its own study rather than mixed in here, since changing the harness changes what the number means.
